# Note tags

## 1. What changes and why

Notes gain tags. A note can be created with tags, every note response carries them,
and the list endpoint can filter by tag. There is production data already, so the
upgrade must leave old notes with an empty tag list.

## 2. Request and response shapes

### POST /notes

```json
{ "title": "Quarterly review", "body": "…", "tags": ["work", "Urgent"] }
```

- `tags` is optional. If present it must be an array of strings (`null` is rejected,
  same treatment as `body`).
- Each tag is trimmed; the trimmed length must be 1–32 (JavaScript string length,
  same measure as `title`).
- Duplicate tags within one note are removed, case-sensitively, keeping the first
  occurrence (`["a", "A", "a"]` → `["a", "A"]`).
- After deduplication at most 10 tags remain; otherwise `400 invalid_tags`.

Response `201` (this is now the note shape everywhere):

```json
{ "id": 1, "title": "Quarterly review", "body": "…", "created_at": "…", "tags": ["work", "Urgent"] }
```

### GET /notes and GET /notes/:id

Every note carries `tags`, an array that is empty when the note has none.

### GET /notes?tag=work&limit=10

Returns only notes carrying that exact tag, newest first, combinable with `limit`.
The parameter is trimmed before matching (a tag can never start or end with
whitespace, since create trims). `?tag=` or whitespace-only is rejected with
`400 invalid_query`. Matching is exact and case-sensitive, like storage. A tag
longer than 32 characters simply matches nothing.

Error responses keep the single shape `{ "error": { "code", "message" } }`; the one
new code is `invalid_tags`.

## 3. Schema change and existing rows

New migration `migrations/002_add_tags.sql`:

```sql
ALTER TABLE notes ADD COLUMN tags TEXT NOT NULL DEFAULT '[]';
```

Tags are stored as a JSON array of strings in the `notes` row itself:

- Storage is verbatim after trimming: no lowercasing, no unicode normalization,
  order of first occurrences preserved. Comparison is case-sensitive end to end
  (SQLite `TEXT` comparison uses BINARY collation, and so does the filter).
- Deleting a note deletes its tags with the row — nothing extra to clean up.
- The default `'[]'` gives every existing row an empty tag list on upgrade; new
  rows always insert an explicit value.

Rejected alternative: a normalized `note_tags(note_id, tag)` table. It indexes well
but needs an extra position column to preserve order, a second query per read, and
application-side reassembly — not worth it at this scale. The `?tag=` filter walks
the table via `json_each`, which is fine here and noted as a scaling limit below.

## 4. Out of scope

- Editing notes (no PATCH/PUT endpoint exists; tags can only be set at creation).
- Filtering by several tags at once (`?tag=a&tag=b` uses the first value only).
- Tag listing, autocomplete, or counts; case-insensitive matching.
- Indexing for tag queries (full scan via `json_each` is acceptable at current
  data volume; revisit if tag filtering becomes hot).
